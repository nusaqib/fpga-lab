# Build system conventions

Every buildable thing in this repo (a curriculum module, a project) is a
directory with its own `Makefile` that includes the shared includes in
`common/mk/`. Nothing is checked in pre-built; everything under `_out/` is
regenerated by `make` and is gitignored.

## Generating a project / bitstream, step by step

```sh
cd curriculum/00_first_bitstream        # or any other module

make BOARD=nexys4 bitstream             # BOARD defaults to nexys4 if omitted
make BOARD=rfsoc4x2 bitstream
make BOARD=blackboard bitstream
```

Each invocation, if the target doesn't already exist, kicks off a full
Vivado batch run (`create_project` -> add sources/constraints -> `synth_1` ->
`impl_1` -> `write_bitstream`) and prints Vivado's own progress to the
terminal - expect this to take anywhere from under a minute (tiny designs on
a 7-series part) to several minutes (RFSoC4x2's larger UltraScale+ device),
and longer the very first time a given part's device libraries get cached.

**Where things land** (all gitignored, all safe to delete):

```
<module>/_out/<board>/vivado/
  <module_name>.xpr                       <- open this in the Vivado GUI
  <module_name>.runs/synth_1/...          <- synthesis logs/reports
  <module_name>.runs/impl_1/...
                ..../<top>.bit             <- the bitstream
  vivado.log                              <- this INVOCATION's log/journal
  vivado.jou
```

Note `vivado.log` is per-*invocation*, not per-project: any `make` target
that runs Vivado again (e.g. `make xsa` after `make bitstream`) overwrites
it. When diagnosing a failure, read the log **before** re-running anything -
this has cost real debugging time twice.

Other targets, run from inside the same module directory:

| Command | Effect |
|---|---|
| `make BOARD=<b> synth` | synthesis only, stops before implementation |
| `make BOARD=<b> gui` | opens the generated `.xpr` in the Vivado GUI |
| `make BOARD=<b> program` | pushes the bitstream over JTAG (board must be connected) |
| `make BOARD=<b> board-info` | prints the resolved part number / paths without building anything |
| `make BOARD=<b> clean` | deletes that board's `_out/` for this module |
| `make clean-all` (repo root) | runs `clean` in every module at once |
| `make sim` | runs the module's default testbench (`sim/tb_*.v`) via `xvlog`/`xelab`/`xsim` - no board, no project |
| `make SIM_TOP=tb_other sim` | runs a specific testbench when a module has more than one |
| `make sim-all` | runs every testbench in `sim/`, stopping at the first failure |
| `make BOARD=<b> xsa` | exports the hardware platform (`.xsa`) for software flows (Tier 5+) |
| `make BOARD=<b> elf` | builds the bare-metal C app against the XSA via the Vitis Python interface (Tier 5+; set `CPU`, optional `BSP_LIBS`) |
| `make BOARD=<b> ooc` | out-of-context synthesis of `OOC_TOP` (defaults to `TOP`): prints one `OOC RESULT: LUT/FF/DSP/BRAM` line, no pins needed (module 20+) |
| `make hls-csim` / `hls-synth` / `hls-cosim` / `hls-package` | the HLS unified flow for modules with an `hls/` dir (`HLS_TOP`; `HLS_PKG=ip_catalog` for BD-consumable IP) (Tier 7+) |

Two optional hooks a module Makefile can set (see modules 10/26 and every
BD-based module since 13): `BD_TCL` - a script creating block design(s),
sourced on first build with the wrapper auto-generated (the BD wrapper can
BE the top: `TOP := <bd>_wrapper`); `IP_TCL` - a script creating standalone
IP, sourced every build, must guard its own idempotency. Hand-written RTL
placed in a BD as a *module reference* needs the `X_INTERFACE_INFO`
attribute idiom - `curriculum/15_custom_ip_from_ps/hdl/axil_regs.v` is the
annotated reference (including the deliberately-absent `FREQ_HZ`).

Simulation output lands in `_out/sim/` (board-independent - there's no
`BOARD=` for `sim`, since a behavioral testbench doesn't need a part/board at
all). See `curriculum/01_combinational_logic/` for the first module using
this - it also documents the self-checking testbench convention (`$display`
a `PASS`/`FAIL` line `make sim` greps for).

Since artifacts are gitignored and regenerated on demand, `git status` should
always be clean of `_out/` content, `.xpr` files, or `.bit` files - if you see
any of those tracked, something's wrong with `.gitignore` for that path.

### If Vivado refuses to launch (licensing)

`ERROR: ... a valid license was not found` means Vivado couldn't validate the
license file against this machine - most commonly because the license is
node-locked to a HOSTID that doesn't match the machine's actual Ethernet MAC
(`ip link show`). That's a licensing/environment problem to fix with your AMD
account, not something in this repo - once a matching license is in place
under `~/.Xilinx/`, `make bitstream` works with no other changes.

## Layout of a hardware (HDL) module

```
some_module/
  README.md          # concept notes for this module
  hdl/                # board-agnostic Verilog/VHDL sources
  constraints/        # per-board XDC snippets, e.g. constraints/nexys4.xdc
  Makefile            # includes common/mk/{common,vivado}.mk
  _out/                <- gitignored, created by `make`
    nexys4/vivado/...
    rfsoc4x2/vivado/...
```

Build for the default board:

```sh
make bitstream
```

Build/switch board:

```sh
make BOARD=rfsoc4x2 bitstream
```

Other targets: `make synth` (synthesis only), `make gui` (open the generated
`.xpr` in the Vivado GUI), `make program` (push the bitstream over JTAG),
`make clean` (delete `_out/`), `make board-info` (print resolved variables).

## Why project-mode, not pure non-project batch mode

`common/tcl/build_project.tcl` creates a real `.xpr` Vivado project under
`_out/<board>/vivado/` (not a throwaway non-project synth run) specifically so
the result can be opened and explored in the Vivado GUI afterwards - reports,
schematic viewer, timing analysis, etc. The script is idempotent: re-running
`make bitstream` reopens the existing project and re-syncs sources instead of
recreating it from scratch, so incremental builds stay fast.

## Layout of a software (Vitis) module

Introduced at `curriculum/13_zynq_ps_bringup` (XSA export) and
`curriculum/14_bare_metal_gpio_and_interrupts` (first ELF); the module is
still ONE directory - hardware and software sides share it:

```
some_zynq_module/
  bd/                  # block-design Tcl (the PS + peripherals)
  hdl/                 # any fabric RTL (module references, tops)
  constraints/         # per-board XDC
  src/                 # C application sources (copied into the Vitis app)
  Makefile             # includes common/mk/{common,vivado,vitis}.mk and
                       # sets CPU (ps7_cortexa9_0 / psu_cortexa53_0 /
                       # microblaze_riscv_0), optionally BSP_LIBS (lwip220)
  _out/
    <board>/vivado/...              # .xpr, bitstream, <module>_<board>.xsa
    <board>/vitis_ws/...            # platform + app, ELF under .../build/
```

`make xsa` exports the platform; `make elf` regenerates the whole Vitis
workspace from it every time (the BSP is a build artifact, never edited).
XSCT is disabled in 2026.1 - `common/tcl/build_app.py` drives the Vitis
Python interface instead; see `docs/tool_setup.md`.

## Embedded Linux (EDF/Yocto) modules - Tier 6

The Linux flow chains three tools, all wrapped by the module Makefile
(introduced at `curriculum/16_edf_linux_bringup`):

```
make xsa                      # same hardware export as any Tier-5 module
sdtgen                        # XSA -> System Device Tree (Vitis ships it)
gen-machineconf parse-sdt     # SDT -> Yocto MACHINE definition
bitbake <image>               # Yocto builds boot firmware + disk image
```

The Yocto workspace is SHARED and lives outside the repo at `~/yocto/edf`
(50+ GB build trees don't fit the per-module `_out/` convention; downloads
and sstate-cache are reused across boards and modules). Setup and rationale:
`docs/tool_setup.md`. PetaLinux is deliberately not used - it is EOL-bound,
superseded by EDF.

## Adding a new board

1. `boards/<name>/board.mk` - set `FPGA_PART` (and `BOARD_PART` if known).
2. `boards/<name>/xdc/` - vendor a real master XDC/constraint set if one
   exists upstream; never hand-type pin numbers from memory (see
   `boards/blackboard/docs/README.md` for what to do when it doesn't exist).
3. `boards/<name>/docs/README.md` - specs + sources, following the existing
   board READMEs as a template.
4. Optionally `boards/<name>/board_files/` if Vivado board_files exist
   upstream.
